# AgroGrant

Бот MAX «Хакатон МАХ 232» (`@t232_hakaton_max_bot`) работает через Long Polling. Он просит ИНН или ОГРН, получает регистрационные данные через Checko API и сохраняет профиль в PostgreSQL.

- `frontend/` — мини-приложение MAX на React и TypeScript.
- `backend/` — API, MAX-боты, подбор и уведомления на TypeScript.
- `worker/` — сбор документов и обработка через GigaChat на Python.
- `docs/` — архитектура, сценарии, источники и факты для презентации.
- `backend/migrations/` — схема PostgreSQL.

## Запуск бота

1. В корневом `.env` задайте `BOT_TOKEN_MAX`, `CHECKO_API`, `DATABASE_URL` и `GIGA_API_KEY`. Сам файл не добавляйте в Git.
2. Выполните `cd backend`, затем `npm ci`. Если база из URL ещё не существует, выполните `npm run db:create`.
3. Выполните `npm run start`. Миграция таблиц применяется при запуске.
4. Откройте бота в MAX, отправьте `/start`, затем ИНН или ОГРН хозяйства.

`npm start` собирает TypeScript и запускает бота. Для разработки с перезапуском при изменении файлов используйте `npm run dev`.

После поиска хозяйства GigaChat определяет несколько направлений по текстовым названиям зарегистрированных ОКВЭД. Команда `/classify` повторяет классификацию сохранённых ОКВЭД без повторного запроса к Checko. Команда `/activity <описание>` позволяет указать фактическую деятельность и обновить направления; `/activity` показывает текущие метки. `/profile` показывает сохранённое хозяйство, `/change` позволяет указать другое, `/help` показывает подсказку. По умолчанию используется модель `GigaChat-2`; при необходимости её можно изменить через `GIGACHAT_MODEL` в `.env`. SDK сам использует стандартный scope для физлица. В MVP у одного пользователя MAX хранится один профиль. Checko возвращает сведения об указанной организации или ИП и не подтверждает, что она принадлежит владельцу аккаунта MAX.

После регистрации бот показывает меню. `/support` открывает карточки мер, подходящих по направлению и региону работы хозяйства; кнопки листают их в одном сообщении. Подтверждённые совпадения идут первыми; меры со статусом `needs_review` и конкретными направлениями показываются после них с пометкой «Предварительное совпадение», чтобы пользователь проверил условия вручную. Регион по умолчанию берётся из регистрации в Checko, его можно уточнить через `/region <название>`. Пока классификация мер не завершена, `/catalog` позволяет просматривать меры региона с явной пометкой о непроверенной применимости. И `/support`, и `/catalog` показывают только меры с указанным дедлайном не раньше текущей даты по Москве; меры без дедлайна скрыты до проверки срока. `/applications` открывает выбранные пользователем меры и позволяет вручную отмечать этап оформления. Кнопка «Хочу податься» сохраняет меру в списке пользователя и не отправляет заявление в ведомство. Прямую ссылку на подачу бот показывает, когда она заполнена в каталоге. Поля карточки `short_description`, `support_type`, `application_url` и связь программы с отбором `parent_measure_id` добавлены в схему; сбор и заполнение этих полей — отдельная задача worker.

Сейчас используется Long Polling: одновременно с Webhook-подпиской он не работает. При размещении на сервере с HTTPS перейдём на Webhook.
